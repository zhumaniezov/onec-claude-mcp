# Проверка версии 2.3.0 и расширения 1.3.0

## Статус

Изменения 2.3.0 покрыты автотестами коннектора: предпросмотр с полем `posting`, отказ старого расширения, запрет физического удаления проведённого документа, операции `post` и `unpost`, разбор кодов отказа `/v1/change`, очистка и ограничение сообщений 1С, флаг профиля `writeMessages` и запись отказов в журнал. В отдельном окружении Linux прошли 64 теста, 2 пропущены как специфичные для Windows.

Модуль расширения 1.3.0 изменён в исходниках. Сборка CFE и приёмка на базе 1С ещё не выполнены.

## Приёмка на стенде 1С перед выпуском

Повторите на отдельной базе со стендом из протокола 2.1.1: документ с суммой 10 и движениями 4 и 6.

| Сценарий | Ожидаемый результат |
| --- | --- |
| `update` проведённого документа: сумма 10 → 20 | HTTP 200, `posted = true`, `reposted = true`. Движения пересчитаны под 20, версия данных новая. |
| `update` с отказом проведения, например при нехватке остатков | HTTP 422 `posting_failed` с текстами сообщений. Документ и движения совпадают со снимком до попытки. |
| `mark` проведённого документа | Пометка удаления установлена, `Проведен = Ложь`, движений нет. |
| `post` и `unpost` | Движения формируются и удаляются. `unpost` непроведённого документа — 422 `not_posted`. |
| `delete` проведённого документа | 422 `posted_document`, документ и движения без изменений. |
| Пользователь без права Проведение изменяет проведённый документ | 403 `posting_forbidden`, ничего не записано. |
| Документ текущей даты с разрешённым оперативным проведением | Проведение в оперативном режиме, как из формы. |
| Коннектор 2.3.0 с расширением 1.2.1 | Предпросмотр изменения проведённого документа отклоняется с просьбой обновить расширение. |

# Протокол версии 2.2.0

Испытания прошли на Windows x64 с файловой 1С **8.3.27.1644**, расширением **1.2.1** и локальной публикацией Apache по HTTPS. Для проверки создали отдельную базу, пользователя записи и два случайных пароля. Один назначили пользователю 1С, второй использовали для проверки отказа. Рабочие учётные данные в испытании не участвовали.

## Диспетчер учётных данных

- Штатная команда `--credential-set` приняла Basic и Bearer в интерактивной консоли. Проверка сравнила содержимое консольного буфера с тестовыми секретами. Ввод через канал был отклонён.
- Повторное создание потребовало `--replace`. После замены MCP соединился с тестовым HTTP-сервисом с новыми данными. Другой адрес публикации с тем же `credentialRef` потребовал отдельной записи.
- Нативная запись имеет тип Generic и область действия текущего пользователя на этом компьютере. Для всей сериализованной записи, включая служебные поля, действует лимит Windows в 2560 байт. Коннектор проверяет размер до записи. [Спецификация Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw)

## Проверка на 1С и в Claude Code

1. Проверочный процесс создал чистое окружение для **Claude Code 2.1.317** и сравнил передаваемые значения с двумя тестовыми паролями и их представлениями HTTP Basic. В окружение включили обычную контрольную переменную. В запущенных Claude инструментах она обнаружилась, а совпадений с секретами не было. Проверка возвращала только результат сравнения.
2. Claude Code зарегистрировал stdio-коннектор, выполнил `onec_get` и получил созданную на стенде запись. Ответы модели для выбора инструментов формировал локальный имитатор Messages API. Через встроенный Bash выполнили проверку окружения. Для wheel также проверили окружение непосредственно в дочернем процессе MCP перед запуском сервера. Проект, каталог настроек Claude и журналы сеанса были выделены под этот прогон.
3. Через MCP выполнили чтение, создание и изменение на стенде. Правильный пароль дал доступ, ошибочный вернул HTTP 401. Прочитали результат записи командой `--audit-show`. В SQLite и журнале регистрации 1С обнаружили ожидаемый логин.
4. Сверили stdout и stderr клиентов, обмен MCP, обращения к локальному Messages API, файлы профиля и сеанса Claude, SQLite, журнал Apache и журнал регистрации 1С. Искали оба пароля и Base64 от `логин:пароль` в UTF-8 и UTF-16. В проверенных каналах совпадений с секретами не обнаружено.

На окончательном wheel проверка охватила 34 файла. При последующем прогоне с EXE просмотрели 40 файлов в каталогах того же стенда, включая накопленные результаты. Claude запускал EXE напрямую. После остановки стенда повторили поиск по сохранённым файлам, удалили обе тестовые записи из Диспетчера и подтвердили их отсутствие. Эти результаты относятся к указанной версии Claude и настройкам журналов стенда. При включении трассировки заголовков HTTP администратор публикации или шлюза может записать заголовок авторизации. [Границы защиты и переход с 2.1.1](../README.md#границы-защиты)

## Сборки и воспроизведение

Из исходников и из установленного wheel прошли по **54 теста**. Оба поставляемых варианта прошли отдельную проверку штатной команды настройки в интерактивной консоли Windows и тестов stdio.

Выполните `python -m unittest discover -s tests -v` под той учётной записью Windows, где доступен Диспетчер учётных данных. Чтобы проверить stdio-сценарии готового EXE, задайте `ONEC_TEST_EXE` с полным путём к нему и повторите команду. Тест `test_stdio_child_reads_native_wincred_for_basic_auth` проверяет получение учётных данных отдельным процессом и аутентификацию на двух адресах локальной публикации. Он выявил отсутствие зависимости `win32timezone` в промежуточной сборке EXE и прошёл на исправленной.
